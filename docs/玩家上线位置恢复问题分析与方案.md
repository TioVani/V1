# 玩家上线位置恢复问题分析与方案

> 问题：玩家下线后再上线，位置总是回到图一中传送到图二的传送阵坐标上，而非下线时的位置。

---

## 一、数据存储脉络回顾

玩家位置持久化链路：

```
WorldMapPlayer._pos  ──saveProgress()──>  worldMapProgress.worlds[worldId].playerPos  ──flush()──>  localStorage
```

- **`saveProgress()`** 调用时机：传送前（来源世界）、战斗返回、背包返回、tutorial 返回等。每次保存的是**当前世界**的 `_pos`。
- **`restoreProgress()`** 调用时机：`loadWorld()` 内部，仅当该世界之前被访问过时，才从存档 `playerPos` 恢复位置。

存档结构：

```
worldMapProgress: {
  currentWorldId: "world_01",   // 记录最近所在的世界 ID
  worlds: {
    "world_01": { playerPos: {x, y}, entities: {...} },
    "world_02": { playerPos: {x, y}, entities: {...} },
    ...
  }
}
```

`currentWorldId` 在每次 `saveProgress()` 时更新（`WorldMapExploration.js` L73），但游戏重新上线时并未用它来决定加载哪个世界。

## 二、根因分析

### 2.1 游戏上线入口 hardcode 加载 world_01

```3872:3876:V1/game.js
            onComplete: function() {
                _log('过场播放完毕，进入大地图');
                stateMachine.transitionTo(GAME_STATE.WORLDMAP);
                if (worldMapSystem) worldMapSystem.loadWorld('world_01');
```

无论玩家上次在哪个世界下线，重新打开游戏永远从 `world_01` 开始。存档中的 `currentWorldId` 字段（记录了最近所在的世界）完全没有被使用。

### 2.2 world_01 的存档位置可能是传送阵坐标

从 world_01 传送到 world_02 的流程：

```4005:4006:V1/game.js
                    worldMapSystem.saveProgress();
                    worldMapSystem.loadWorld(result.targetWorld, fromWorld);
```

1. `saveProgress()` — 此时 `_currentWorldId` 仍为 `world_01`，将 world_01 的 `_pos`（即 `portal_01_02` 坐标 `(1274, 80)`，因为玩家必须站到传送阵上才能触发）写入存档
2. `loadWorld('world_02', 'world_01')` — 加载 world_02

这意味着存档中 `world_01.playerPos` 被锁定在了玩家离开 world_01 时的位置，即 portal_01_02 坐标 `(1274, 80)`。

### 2.3 上线恢复流程

`loadWorld('world_01')` 内部（`WorldMapSystem.js` L56-89）：

```javascript
function loadWorld(worldId, fromWorldId) {
    player.init(config);          // _pos = playerStart = (215, 750)
    var visited = isWorldVisited(pd, worldId);   // world_01 已访问 → true
    if (visited) {
        restoreProgress(pd);       // _pos = 存档中的 playerPos = (1274, 80)
    }
    if (fromWorldId && ...) {     // fromWorldId = undefined → 不执行
        // portal 落点逻辑
    }
}
```

1. `init()` 将 `_pos` 重置为 playerStart `(215, 750)` — world_01 出生点
2. `restoreProgress()` 将 `_pos` 覆盖为存档中的 `playerPos` `(1274, 80)` — 即 portal_01_02 坐标

**结论：玩家出现在 `(1274, 80)`，恰好是图一中传送到图二的传送阵位置。**

### 2.4 为什么"每次都"在这？

因为只要玩家从 world_01 去过 world_02 一次，world_01 的存档 `playerPos` 就被锁定在 portal_01_02 坐标 `(1274, 80)`。除非：

- 玩家之后回到 world_01 并在其中走动，触发新的 `saveProgress()`（如战斗返回、NPC 交互返回等），`playerPos` 才会被更新为其他坐标
- 玩家回 world_01 并正常退出时，如果游戏有退出前 saveProgress（但纯前端游戏通常没有"正常退出保存"机制——浏览器页面关闭时 localStorage 不一定被写入）

**如果玩家从 world_01 去 world_02 后，在 world_02 中下线**：再上线时加载 world_01，存档位置仍是 portal_01_02。world_02 的存档位置虽然正确，但游戏不会加载 world_02。

**如果玩家回到 world_01 走动后，又在世界内触发过 saveProgress**：此时 world_01 的 playerPos 会被更新，上线时就不是传送阵位置了。但跨世界传送前的 saveProgress 是 immediate=true 的立刻写（`WorldMapExploration.js` L82），如果后续没有新的 saveProgress，portal 坐标就是最后一次写入。

### 2.5 传送阵坐标与 playerStart 的比较

以 world_01 为例：
- playerStart：`(215, 750)` — 第一次进入 world_01 的出生点
- portal_01_02 坐标：`(1274, 80)` — 传送到 world_02 的传送门

两者完全不同。所以能确定问题中的"传送阵"指的就是 portal 坐标 `(1274, 80)`，而非 playerStart。

## 三、优化方案

### 方案 A：上线时根据存档 currentWorldId 加载对应世界（推荐）

**思路**：上线入口不再 hardcode `world_01`，而是从存档读取 `currentWorldId`，加载玩家最近所在的世界。

**修改位置 1**：`V1/game.js` L3875

```javascript
// 改动前：
if (worldMapSystem) worldMapSystem.loadWorld('world_01');

// 改动后：
var lastWorld = (saveData && saveData.worldMapProgress && saveData.worldMapProgress.currentWorldId) || 'world_01';
if (worldMapSystem) worldMapSystem.loadWorld(lastWorld);
```

**修改位置 2**：过场动画逻辑。如果 `lastWorld` 不是 `world_01`，需要考虑是否跳过 world_01 的剧情过场。这个需要根据过场系统的设计来决定处理方式。

**影响**：
- 玩家在 world_02 下线 → 上线直接进入 world_02，在 world_02 上次的位置
- 玩家在 world_01 非传送阵位置下线 → 世界不变，仅位置正确（纯世界内位置恢复）
- 新玩家首次进入 → `currentWorldId` 为 null → 回退到 `world_01`

**风险**：
- 过场动画目前固定为 world_01 剧情，切换到其他世界需要确认过场逻辑
- 如果玩家上次在塔类（world_13-16），上线进塔需要确认塔的初始化逻辑

### 方案 B：恢复存档 world_01 的 playerPos 后，额外用 currentWorldId 判断是否需要跨世界加载

**思路**：保持上线加载 world_01 不变，但在加载完成后，检查 `currentWorldId`。如果不是 world_01，自动进行一次跨世界加载。

**修改位置**：`V1/game.js` L3873-3875 周边

```javascript
onComplete: function() {
    stateMachine.transitionTo(GAME_STATE.WORLDMAP);
    // 先加载 world_01（为过场）
    worldMapSystem.loadWorld('world_01');
    // 如果上次在别的世界，自动切过去
    var lastWorld = saveData.worldMapProgress.currentWorldId;
    if (lastWorld && lastWorld !== 'world_01') {
        setTimeout(function() {
            worldMapSystem.loadWorld(lastWorld);
        }, 100);
    }
}
```

**缺点**：会触发两次 `loadWorld()`，第一次 world_01 的初始化可能产生不必要的副作用（如过场渲染），且两次加载之间可能有闪烁。

### 方案 C：入口处恢复到 world_01 后，用户自行走到之前的世界

不做任何改动。现状上，玩家从 world_01 走到 portal_01_02 传送到 world_02 后，world_02 的位置由存档恢复（如果 `visited` 为 true，portal 落点逻辑在方案讨论后已修复的话），玩家可以自动回到 world_02 的存档位置。

**但问题在于**：如果 portal 落点逻辑覆盖了存档（当前 behavior），即使走到了 world_02，位置也是 portal 坐标而非存档位置。参见之前的 portal 落点逻辑相关修复。

## 四、推荐方案与影响评估

**推荐方案 A**，理由：

1. **语义最正确**：玩家上次在哪个世界、哪个位置，上线就应该回到那个世界、那个位置
2. **改动最小**：仅一行变更（`'world_01'` → `lastWorld`）
3. **和现有存档结构一致**：`currentWorldId` 字段本来就存在且被维护，只是没被消费
4. **覆盖全部场景**：
   - world_01 下线 → 回 world_01 + 存档位置 ✓
   - world_02 下线 → 回 world_02 + 存档位置 ✓
   - 任意世界下线 → 回对应世界 + 存档位置 ✓
   - 新玩家 → 回退 world_01 ✓

**方案 A 的前提条件与约束**：

1. **过场动画**：当前过场是一段通用世界观旁白（4 条文案），不绑定特定世界。对于回访玩家，`skippable: true` 允许跳过。如果希望进一步优化体验，可以在 `onStartClick` 中检查 `currentWorldId` 是否存在，存在则跳过过场直接进入 worldmap。但这不是必须的。

2. **BGM 切换**：当前代码在 `onComplete` 中播放 `shuhanTheme` 并加载 world_01。如果 `lastWorld` 是其他世界（如 `world_17` 冥境），需要切换对应 BGM。`game.js` L4006-4009 已有先例——传送时检查 `targetWorld === 'world_17'` 来切换 BGM。推荐在方案 A 实现时将此 BGM 切换逻辑封装为通用函数，供上线入口和跨世界传送共用：

```javascript
// 上线入口处
var lastWorld = (saveData && saveData.worldMapProgress && saveData.worldMapProgress.currentWorldId) || 'world_01';
if (lastWorld === 'world_17') {
    audioSystem.enterArdeacinerea();
} else {
    audioSystem.playBgm('shuhanTheme', 0.4);
    audioSystem.fadeBgmVolume(0.32, 5000);
}
worldMapSystem.loadWorld(lastWorld);
```

3. **`loadWorld` 通用性**：已验证 `loadWorld` 对所有世界走相同初始化流程（init → visited 检查 → restoreProgress → portal 落点），不含 world_01 特有逻辑。此点无风险。

4. **新玩家首次上线**：`currentWorldId` 为 null → 回退到 `world_01` → 行为和当前完全一致。

## 五、portal 落点逻辑的关联审查

审计过程中同时审查了 `WorldMapSystem.loadWorld()` 中的 portal 落点逻辑：

```javascript
// 步骤 3：portal 落点覆盖（在 restoreProgress 之后执行）
if (fromWorldId && config.entities) {
    for (...) {
        if (e.type === 'portal' && e.targetWorld === fromWorldId) {
            player.setPlayerPos(e.x, e.y);
        }
    }
}
```

该逻辑在**跨世界传送**场景中的影响：

- 玩家从 world_01 portal 到 world_02：`loadWorld('world_02', 'world_01')` → portal 落点 = world_02 中指向 world_01 的 portal 坐标（即 `(116, 746)`，与 world_02 的 playerStart 相同）
- 如果 world_02 已被访问过，步骤 2 `restoreProgress()` 恢复了存档位置，但步骤 3 将其覆盖为 portal 坐标

**但是**，在大多数世界里，portal 坐标恰好等于 playerStart 坐标（如 `portal_return` 在 world_02 的 `(116, 746)` 和 `start_world_02` 一致）。因此这个覆盖在已访问世界的影响通常等同于"回到出生点"，而非"回到传送阵"。

少数例外——如 `portal_w02_w17` 在 world_02 的 `(1314, 353)`，其回传 portal `portal_w17_w02` 在 world_17 的 `(19, 954)`。如果玩家多次进出 world_17，从 world_02 回 world_17 时会回到 portal 落点 `(19, 954)` 而非存档位置。

**结论**：该逻辑与本次问题（上线恢复）不是同一根因，但如果在方案 A 之后希望"跨世界传送也回到存档位置而非 portal 落点"，可对此逻辑加上 `!visited` 条件。这不是本次修复的必要部分，可作为后续优化。
