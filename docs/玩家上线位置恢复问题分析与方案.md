# 玩家上线位置恢复问题分析与方案（深度审计修正版）

> 问题：玩家下线后再上线，位置总是回到图一中传送到图二的传送阵上，不管玩家在哪个世界下线。

---

## 一、数据存储脉络回顾

### 1.1 核心链路

```
WorldMapPlayer._pos  ──saveProgress()──>  worldMapProgress.worlds[worldId].playerPos  ──GameDataStore.Proxy──>  localStorage
```

- `saveProgress()` 由 `WorldMapExploration.js` L68-81 实现，写 `playerPos` 和 `currentWorldId`
- **GameDataStore 通过 Proxy 自动追踪脏写 + 2000ms 防抖 flush**
- 所有 `savePlayerData()` 注入已被设为 no-op（不再是 StorageSystem 负责写入）

### 1.2 saveProgress 调用时机（全部 12 处，全部事件驱动）

| 场景 | 调用次数 | 位置来源 |
|------|---------|---------|
| 从战斗/教学/UI回到 WorldMap | 多处 | `restoreReturnPosition()` 恢复后的真实位置 |
| **传送门 (portal) 切换世界** | 1 处 | 来源世界 portal 坐标 `(1274, 80)` |
| **触发线 (triggerLine) 切换世界** | 1 处 | 来源世界触发线处坐标 |
| 进塔前 | 1 处 | snapshot 位置（塔旁） |
| 开宝箱 | 1 处 | 即时位置 |

**关键发现**：玩家在任意世界中单纯走动不会触发 `saveProgress()`。没有定时器、没有每帧保存。保存完全是事件驱动的。

### 1.3 世界切换时的 saveProgress 时机

portal 传送（`game.js` L4032-4033）：

```javascript
worldMapSystem.saveProgress();   // _currentWorldId 仍是来源世界
worldMapSystem.loadWorld(result.targetWorld, fromWorld);
```

triggerLine 传送（`game.js` L5772-5773）：

```javascript
worldMapSystem.saveProgress();   // _currentWorldId 仍是来源世界
worldMapSystem.loadWorld(_tl.targetWorld, worldMapSystem.getWorldId());
```

**saveProgress 在 loadWorld 之前调用**。此时记录的：
- `currentWorldId` = 来源世界 ID（如 `world_01`）
- `world_01.playerPos` = portal 坐标 `(1274, 80)`
- **目标世界（world_02）的位置不会被保存**（因为 `_currentWorldId` 还没变成 `world_02`）

## 二、根因分析

### 2.1 完整复现路径

假设玩家在 world_01，意图去 world_02 并在那里下线：

```
Step 1: 玩家走到 portal_01_02 (1274, 80)，点击传送
Step 2: saveProgress()
         ├─ currentWorldId = 'world_01'
         ├─ world_01.playerPos = (1274, 80)   ← 传送阵坐标
         └─ Proxy 标记 dirty，但 2000ms 防抖还没 flush
Step 3: loadWorld('world_02', 'world_01')
         ├─ _currentWorldId = 'world_02'
         ├─ player.init() → _pos = playerStart (world_02 出生点)
         ├─ isWorldVisited('world_02') → 如果是首次进入：false → restoreProgress 不执行
         └─ 如果没有触发任何 saveProgress 事件...
Step 4: 玩家在 world_02 中走动
         ├─ _pos 在内存中随键盘输入更新 ✓
         └─ 不触发 saveProgress，localStorage 不更新 ✗
Step 5: 玩家关闭游戏
         └─ 最后一次写入 localStorage 的数据：
             currentWorldId = 'world_01'
             world_01.playerPos = (1274, 80)
             world_02.playerPos = ??? (可能不存在或为空)
Step 6: 重新打开游戏
         ├─ loadWorld(lastWorldId) → lastWorldId = 'world_01'
         ├─ world_01 visited = true
         ├─ restoreProgress → _pos = (1274, 80) ← 传送阵坐标！
         └─ fromWorldId = undefined → portal 逻辑不触发
```

**结果**：玩家出现在 world_01 的 portal_01_02 坐标 `(1274, 80)`——即图一传送到图二的传送阵。

### 2.2 两个核心根因

**根因 1（世界切换时机）**：portal/triggerLine 传送时，`saveProgress()` 在 `loadWorld()` 之前调用。保存的是来源世界的 portal 坐标，而非目标世界的落点。同时 `currentWorldId` 被写为来源世界。

**根因 2（走动不存档）**：玩家在任意世界中正常走动不会触发 `saveProgress()`。对于首次进入的世界（`visited = false`），`restoreProgress` 不执行，位置完全由 `playerStart` 或 portal 落点决定。如果 portal/triggerLine 传送后从不触发任何 saveProgress 事件就退出，目标世界的位置数据不会进入存档。

### 2.3 为什么之前的上线入口修改（用 currentWorldId）没有解决问题

之前只修改了上线入口处的世界选择（L3875 附近），但 `currentWorldId` 本身在 portal 传送时就被写成了来源世界。所以即使上线时读 `currentWorldId`，读到的仍然是来源世界 + portal 坐标。

## 三、优化方案

### 3.1 修改 1：传送时 saveProgress 移到 loadWorld 之后（核心修复）

**修改位置**：`V1/game.js` 两处

#### Portal 传送（约 L4032-4033）

```javascript
// 修改前：
worldMapSystem.saveProgress();
worldMapSystem.loadWorld(result.targetWorld, fromWorld);

// 修改后：
worldMapSystem.loadWorld(result.targetWorld, fromWorld);
worldMapSystem.saveProgress();
```

`loadWorld` 内部会将 `_currentWorldId` 设为目标世界、设置 `_pos` 为目标世界的落点。之后 `saveProgress` 保存的是目标世界的 `currentWorldId` 和落点位置。

#### triggerLine 传送（约 L5772-5773）

```javascript
// 修改前：
worldMapSystem.saveProgress();
worldMapSystem.loadWorld(_tl.targetWorld, worldMapSystem.getWorldId());

// 修改后：
worldMapSystem.loadWorld(_tl.targetWorld, worldMapSystem.getWorldId());
worldMapSystem.saveProgress();
```

**注意**：这两处修改意味着**不再保存来源世界的离开位置**。如果后续需要"记录离开位置以便返回来源世界时恢复"，可以额外调用一次 saveProgress 保存来源世界（但当前行为本来也只是保存了 portal 坐标，不是真实走动位置）。

### 3.2 修改 2：上线入口用 currentWorldId 加载对应世界（配套修复，已完成）

`V1/game.js` L3896-3907（已完成）：

```javascript
var lastWorldId = (saveData && saveData.worldMapProgress && saveData.worldMapProgress.currentWorldId) || 'world_01';
worldMapSystem.loadWorld(lastWorldId);
```

配合修改 1，`currentWorldId` 现在是目标世界（不是来源世界），上线时会正确加载。

### 3.3 场景验证

修改后的完整流程：

```
Step 1: 玩家走到 portal_01_02 (1274, 80)，点击传送
Step 2: loadWorld('world_02', 'world_01')
         ├─ _currentWorldId = 'world_02'
         └─ _pos = world_02 落点
Step 3: saveProgress()
         ├─ currentWorldId = 'world_02'           ← 正确
         ├─ world_02.playerPos = world_02 落点     ← 正确
         └─ Proxy 标记 dirty，最多 2000ms 后 flush 到 localStorage
Step 4: 重新打开游戏
         ├─ loadWorld('world_02')
         ├─ world_02 visited = true（步骤 3 创建了条目）
         ├─ restoreProgress → _pos = world_02 存档位置 ✓
         └─ fromWorldId = undefined → portal 逻辑不触发
```

如果玩家在 world_02 中触发战斗再走动：
```
Step 5: 战斗结束 → saveProgress
         ├─ currentWorldId = 'world_02'
         ├─ world_02.playerPos = restoreReturnPosition 恢复后的真实位置
         └─ 下次上线：回到真实位置 ✓
```

### 3.4 已知局限：走动仍不存档

方案修复的是"世界切换时 `currentWorldId` 和存档位置被错误写入来源世界"的问题。但**走动不存档的习惯未变**：

- 玩家从 world_01 传送到 world_02 后，saveProgress 保存的是 world_02 的初始位置（playerStart/portal 落点），而非玩家在 world_02 走动后的位置
- 如果玩家在 world_02 走动后未触发任何 saveProgress 事件（战斗、开宝箱、UI 返回等）就退出，上线后会回到初始位置

这不是本次修复的漏洞，而是当前保存机制的整体前提——只有事件驱动保存，无走动时的定时保存。如需要更精细的位置记录，可在 WorldMapSystem 的 `update()` 中增加定时保存（例如每 5 秒或走满一定距离后 saveProgress）。

### 3.5 补充优化：portal 落点逻辑加 visited 条件（可选）

`WorldMapSystem.js` L76-82 的 portal 落点逻辑：

```javascript
// 修改前：无条件覆盖 restoreProgress 恢复的位置
if (fromWorldId && config.entities) { ... }

// 修改后：仅首次进入时覆盖
if (!visited && fromWorldId && config.entities) { ... }
```

此修改确保已访问世界的存档位置不被 portal 落点覆盖。与本次根因不直接相关，但可提高已访问世界回传时的位置一致性。

## 四、影响评估

| 影响 | 详细 |
|------|------|
| **来源世界离开位置丢失** | 跨世界传送时不再保存来源世界位置。如果玩家从 world_01 传送走后再回 world_01，而 world_01 之前没有存档位置，会出现在 playerStart。但当前行为下 world_01 也已有存档位置（来自之前的 saveProgress），所以不影响已有体验。 |
| **防抖延迟** | 2000ms 防抖意味着如果玩家传送后立即关闭页面，新数据可能未写入。可降低防抖时间或增加 `beforeunload` 事件强制 flush。此影响在修改前后都存在。 |
| **过场动画** | 上线入口使用 `lastWorldId`，过场动画仍然是通用世界观旁白（4 条简短文案），不绑定特定世界。无问题。 |
| **BGM** | world_17（冥境）已在上线入口中处理 BGM 切换。其他世界使用默认 `shuhanTheme`。无问题。 |
