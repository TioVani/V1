# 无尽之塔怪物死亡结算 — 最终优化方案

## 背景

初版方案（方案 A：combatTimer 感知 pendingDeaths + 方案 B：cleanupCombat 兜底）已落地到 `TowerSystem.js`，但问题仍未完全解决。

经过 mock 测试验证，BattleEngine 核心链路（`handleStarClick` → `addPendingDeath` → `update` 消散 → `callbacks.onMonsterDeath`）在 `active=true` 且 `preventFinish=true` 条件下是正确的。

根因可能是多因素复合导致：延迟消散的 1150ms 窗口期内，TowerSystem 内部的多个定时器/状态切换路径之间存在未覆盖的竞态。本方案采用更激进的重构——**放弃 `pendingDeaths` 延迟消散机制，在塔模式下直接触发死亡**，从根本上消除所有时序问题。

---

## 一、mock 测试结论

测试文件：`tests/tower-death-chain-mock.test.mjs`

| 测试 | 结果 |
|------|------|
| 基本伤害链路（active=true + 伤害钩子） | PASS：HP 正常扣减、pendingDeaths 正确入队、消散后回调触发 |
| 缺少 active 属性 | PASS：伤害被正确阻断 |
| preventFinish=true/false 消散路径 | PASS：preventFinish=true 直接调回调、false 走 finishBattle |
| onStarHitMonster 防御阻断 | PASS：吸收/护盾正确阻断伤害 |
| destroy 在 pendingDeaths 消散前 | PASS：destroy 后回调不触发（静默丢失） |
| 多帧 update 后正常消散 | PASS：时间到达后回调正常触发 |

结论：**BattleEngine 核心机制在理想条件下完全正常**，问题出在 TowerSystem 与 BattleEngine 的集成层级（状态同步、定时器竞态、渲染时机等）。

---

## 二、优化方案：塔模式跳过 pendingDeaths，直接触发死亡

### 2.1 设计思路

`pendingDeaths` 延迟消散是为了给流星/特效动画留出播放时间。但在塔模式下，消散期间存在的竞态风险（combatTimer、PauseCoordinator、GameBattleRenderer 帧同步）远大于动画收益。

**直接收窄**：在 `handleStarClick` 中，检测到 HP ≤ 0 时，不加入 `pendingDeaths` 队列，直接调用预定回调触发死亡流程。

### 2.2 代码改动

#### 改动点 1：BattleEngine.handleStarClick — 支持直接死亡模式

在 `BattleEngine.js` 中，`addPendingDeath` 之前增加判断：

```js
// handleStarClick 中，hp <= 0 分支（原 BattleEngine.js 第 962-964 行）
if (targetMonster.hp <= 0) {
    if (S.extensions && S.extensions.immediateDeath) {
        // 塔模式：跳过 pendingDeaths，直接触发死亡回调
        safeCall(callbacks.onBeforeMonsterDeath, { monster: targetMonster });
        safeCall(callbacks.onMonsterDeath, { monster: targetMonster, floor: S.floor });
    } else {
        addPendingDeath(targetMonster);
    }
}
```

#### 改动点 2：NormalBattleAdapter.initTowerEngine — 设置 immediateDeath 标志

在 `NormalBattleAdapter.js` 的 `initTowerEngine` 中，扩展配置增加 `immediateDeath: true`：

```js
towerConfig.extensions = {
    onBeforeStarClick: onBeforeStarClickHook,
    getAttackTarget: getAttackTargetHook,
    calculateDamageOverride: calculateDamageOverrideHook,
    onStarHitMonster: onStarHitMonsterHook,
    onScoreEarned: onScoreEarnedHook,
    onStarConsumed: onStarConsumedHook,
    onAfterSpecialStar: onAfterSpecialStarHook,
    preventFinish: true,
    immediateDeath: true   // ★ 塔模式跳过 pendingDeaths，直接触发死亡
};
```

#### 改动点 3：TowerSystem — 移除不再需要的 pendingDeaths 防护

方案 A（`combatTimer` 的 pendingDeaths 检查）和方案 B（`cleanupCombat` 的 `_inCleanupDefend` 兜底）可以保留作为冗余防护，但不再是必要条件。

---

## 三、为什么这个方案更可靠

| 对比维度 | 原方案（pendingDeaths 消散） | 新方案（immediateDeath） |
|----------|------------------------------|---------------------------|
| 时序依赖 | 依赖 1150ms 内 update() 被持续调用 | 无时序依赖 |
| 竞态风险 | combatTimer / PauseCoordinator / renderer 帧同步 | 无竞态风险 |
| 复杂度 | TowerSystem + BattleEngine 双时钟协调 | 单路径，无协调 |
| 回调可靠性 | 回调在 update() 异步触发 | 回调在 handleStarClick 同步触发 |
| 动画影响 | 消散动画完整播放 | 流星动画被跳过（HP 归零时立即切状态） |

---

## 四、影响范围评估

| 文件 | 改动 | 风险 |
|------|------|------|
| `BattleEngine.js` `handleStarClick` | 增加 `immediateDeath` 分支（3 行） | **低**：只在 `extensions.immediateDeath=true` 时生效 |
| `NormalBattleAdapter.js` `initTowerEngine` | 增加 `immediateDeath: true`（1 行） | **低**：仅为塔模式新增一个扩展属性 |
| `TowerSystem.js` | 无需修改（方案 A/B 保留） | 无 |

- 不影响普通模式/赛季模式/Boss 模式（它们的 extensions 不含 `immediateDeath`）
- 不影响 `useSkill` / 闪避反击路径（这些路径直接调 `finishBattle` 或 `defeatMonster`，不经过 `handleStarClick`）
- 不影响隐藏之路 Boss（`isHiddenPathBoss=true` 时不走 BattleEngine 的 `update` 路径）

## 五、替代方案（如果不想改 BattleEngine）

如果不想改动 BattleEngine 的 `handleStarClick`（担心影响其他模式），可以在 TowerSystem 层面做同样的直接死亡逻辑：

**需要两处修改**：

1. 在 `startCombat` 的 `engineConfig` 中增加 `onDamageDealt` 回调：

```js
var engineConfig = {
    monster: combatMonster,
    // ... 其他配置 ...
    onMonsterDeath: function() { defeatMonster(); },
    onPlayerDeath: function() { playerDeath(); },
    onTimeUp: function() { combatTimeout(); },
    onDamageDealt: function(ctx) {
        // 塔模式：HP 归零时直接触发死亡，不等待 pendingDeaths 消散
        if (ctx.monster && ctx.monster.hp <= 0) {
            defeatMonster();
        }
    }
};
```

2. 确保 `handleStarClick` 中 HP 检查在 `onDamageDealt` 之后仍会调 `addPendingDeath`（当前 BattleEngine 代码不改动，`addPendingDeath` 仍会被调用，但 `defeatMonster` → `cleanupCombat` → `battleEngine.destroy()` 已经执行，`pendingDeaths` 被 destroy 重置，无副作用）。

**注意**：`onDamageDealt` 在 `targetMonster.hp -= actualDamage` 之后、`hp <= 0` 检查之前触发（`BattleEngine.js:949-959`），时序正确——回调收到的是已扣血后的 HP 值。
