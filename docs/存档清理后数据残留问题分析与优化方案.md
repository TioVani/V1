# 存档清理后数据残留问题分析与优化方案

## 一、问题现象

清理所有游戏存档数据后，新建角色通过新手战斗解锁 UI，发现角色状态异常：
- 角色 90 级满级
- 材料全部 999 满值
- 所有装备已解锁
- 所有角色已解锁
- 所有灵光（星灵）已解锁
- 灵石（starSource）溢出

预期行为：新角色应从 0 开始，仅拥有初始角色 `char_001`（玉蝉仙，Lv.1），材料、装备、灵光均为空。

---

## 二、存档系统架构概述

| 层级 | 模块 | 职责 |
|------|------|------|
| 存储层 | `BrowserAPI.js` | localStorage 读写，所有 key 加 `game_` 前缀 |
| 存储引擎 | `GameDataStore.js` | 统一存储：`defaultSaveData` 模板、Proxy 自动标脏、防抖 flush(2000ms)、load/reset |
| 迁移层 | `MigrationPipeline.js` | v0→v1→v2→v3 增量迁移、旧数据修复 |
| 兼容层 | `PlayerDataSystem.js` | 兼容存根（no-op），保留旧 `defaultPlayerData` 模板 |
| 调试层 | `DebugSystem.js` | 一键解锁全部功能（`unlock_all` 等调试按钮） |

### localStorage Key 清单

| Key | 用途 |
|-----|------|
| `game_saveData_v3` | v3 统一存档（saveData + runtimeData 分离） |
| `game_playerData` | v2 旧存档（已废弃，但 load 时仍会回退读取） |
| `game_bestScore` | 历史最高分 |
| `game_cloudData` | 排行榜云同步数据 |

### 加载流程（`GameDataStore.load()`）

```
load()
  ├── 尝试读 game_saveData_v3
  │   └── 存在 → _migrateIncomingSaveData(v3data) 字段补全
  ├── 不存在 v3 → 尝试读 game_playerData（旧 key）
  │   └── 存在 → _repairOldData → _migrateV2toV3 → _migrateIncomingSaveData
  ├── 都不存在 → deepClone(defaultSaveData) + deepClone(defaultRuntimeData)
  └── _rebuildProxy() + _resetDirty() + _fireLoadHooks()
```

### 字段补全逻辑（`_migrateIncomingSaveData`）

```
输入：已加载的存档对象 data

操作：
  1. 以 defaultSaveData 做深拷贝作为模板（merged）
  2. 遍历 data 的所有 key，深拷贝覆盖到 merged
  3. merged._version = 3

关键含义：data 中缺失的字段，使用 defaultSaveData 中的值回填。
```

## 三、根因分析

### 根因 1：`reset()` 不会真正持久化

`reset()` 的实现如下：

```javascript
function reset() {
    _rawSave = deepClone(defaultSaveData);    // ① 替换内存数据
    _rawRuntime = deepClone(defaultRuntimeData);
    _rebuildProxy();                           // ② 重建 Proxy
    _resetDirty();                             // ③ 清脏标记 → _dirty = false
    flush();                                   // ④ flush 首行 if (_dirty) → 跳过！
}
```

`flush()` 的开头是 `if (_dirty)`——而 `_resetDirty()` 已将 `_dirty` 置为 `false`，所以 `flush()` 直接跳过，**`game_saveData_v3` 不会被更新**。

**影响**：调用 `reset()` 后，内存中的 `_rawSave` 已经重置为空默认值，但 localStorage 中的 `game_saveData_v3` 仍然是旧数据。下次页面加载时 `load()` 读到旧 v3 数据，完整恢复所有旧状态。

---

如果用户手动删除了 `game_saveData_v3`（通过浏览器 DevTools），但 `game_playerData`（旧 key）仍然存在，`load()` 会回退读取旧 key，通过 `_migrateV2toV3` 完整恢复所有旧数据。

**两种触发场景**：

- **场景 A**：用户先调试解锁了全部内容（`unlock_all`），然后调用了 `reset()`。`reset()` 不 flush → `game_saveData_v3` 仍是满解锁状态 → 下次加载恢复全部。
- **场景 B**：用户手动删除了 `game_saveData_v3`，但没删 `game_playerData` → `load()` 回退读取旧 key → 恢复全部。

两个地方的默认值模板都包含 `starSource: 9999`：

| `PlayerDataSystem.js` → `defaultPlayerData.starSource` | `9999` |

## 四、优化方案

### 方案一：修复 `reset()` 的 flush 逻辑（核心修复）

**修改文件**：`V1/src/systems/GameDataStore.js`

**修改点**：`reset()` 中，在 `_rebuildProxy()` 之后先 `_markDirty()`，再 `flush()`。

改前：

```javascript
function reset() {
    _rawSave = deepClone(defaultSaveData);
    _rawRuntime = deepClone(defaultRuntimeData);
    _rebuildProxy();
    _resetDirty();
    flush();
}
```

改后：

```javascript
function reset() {
    _rawSave = deepClone(defaultSaveData);
    _rawRuntime = deepClone(defaultRuntimeData);
    _rebuildProxy();
    _markDirty();   // 显式标脏，确保 flush 会执行
    flush();
}
```

---

### 方案二：`reset()` 时同步删除旧 key（防御性修复）

**修改文件**：`V1/src/systems/GameDataStore.js`

**修改点**：`reset()` 中调用 `removeStorage('game_playerData')` 清除旧 key 残留。

```javascript
function reset() {
    _rawSave = deepClone(defaultSaveData);
    _rawRuntime = deepClone(defaultRuntimeData);
    _rebuildProxy();
    _markDirty();
    flush();
    // 清除旧 key 残留，防止下次 load() 回退读取
    try {
        removeStorage('playerData');
        removeStorage('bestScore');
    } catch (e) {
        console.error('[GameDataStore] reset 清理旧 key 失败:', e);
    }
}
```

**注意**：`removeStorage` 需要通过 `deps` 注入。当前 `createGameDataStore` 的 deps 中已有 `removeStorage`，需要在 `reset()` 中使用它。

---

### 方案三：修正默认值中的调试值

**修改文件**：
- `V1/src/systems/GameDataStore.js` → `defaultSaveData.starSource`
- `V1/src/systems/PlayerDataSystem.js` → `defaultPlayerData.starSource`

**修改点**：`starSource: 9999` → `starSource: 0`

---

### 方案四（可选）：`load()` 增加旧 key 清理

在 `load()` 成功加载 v3 数据后，主动删除旧 key `game_playerData`，防止未来某天 v3 key 丢失时回退到旧数据。

```javascript
// 在 _migrateV2toV3 分支的最后添加：
try { removeStorage('playerData'); } catch(e) {}
```

## 五、影响范围

| 修改项 | 影响系统 | 风险 |
|--------|---------|------|
| `reset()` 加 `_markDirty()` | GameDataStore | 无风险，修正确保持久化 |
| `reset()` 删旧 key | GameDataStore | 低风险：删除已废弃的旧 key |
| `starSource: 0` | GameDataStore + PlayerDataSystem | 需确认：是否有业务逻辑依赖 9999 初始值（如教程中引导消费灵石） |
| `load()` 后删旧 key | GameDataStore | 低风险：一次性的旧 key 清理 |

**关于 `starSource` 初始值的风险说明**：

如果教程流程中引导玩家使用灵石（如抽卡教学），初始 0 灵石会导致教程卡死。需要在修改前确认教程流程的灵石消耗设计。如果教程确实需要初始灵石，应将 9999 改为一个合理的教学起始值（如 100~500），并在代码注释中标注"教学初始值"而非"调试值"。

   - 调试解锁全部 → 调用 `reset()` → 刷新页面 → 确认数据已清空
