# 灵光点击手感优化方案 — 统一触摸管道

## 一、问题现象

1. **第一次点击无反应，第二次才发动**
2. **连续点击四五次无反应**
3. **下落模式点击完全无反应**

---

## 二、根因：当前架构的结构性缺陷

当前触摸事件链是一个**隐式优先级树**，分布在 `game.js`、`TouchGestureSystem`、`NormalBattleAdapter`、`BattleEngine` 四个层级中。每个节点独立判断、独立过期、独立消费，节点间通过 `return`/`continue`/`return false`/`return true` 隐式传递控制权。

这导致 7 个已识别问题中的 5 个不是孤立 bug，而是架构自身的产物：

| 问题 | 架构根源 |
|------|----------|
| 问题1：stunned 过期不自洽 | 4 层 each 独立维护过期逻辑，没有统一的"玩家状态门" |
| 问题2：节奏阶段误吞 | 没有"消费 vs 穿透"的显式协议，全有或全无 |
| 问题4：双击竞态 | TouchStart / TouchEnd 跨生命周期状态传递依赖隐式引用（`_charging`）而非显式管道上下文 |
| 问题5：打断检查四层不一致 | 同上：每层自己写一遍"被打断怎么办" |
| 问题7：活动手势冲突 | `handleGestureStart` 不知道自己是第几次被调用，无状态保护 |

**按补丁模式修**需要 6 个方案 6 个文件，审计两轮发现 12 条修正。因为补丁模式在修补症状而非重构架构。

**按统一管道模式修**只需新建一个模块（~150 行），对现有模块做适配性修改（不是重写）。

---

## 三、统一触摸管道设计

### 核心理念

把触摸生命周期（TouchStart→TouchMove→TouchEnd）变成一条**显式的中间件管道**，每个消费者系统注册为一个中间件，管道按优先级顺序执行中间件，中间件返回明确的三种结果决定控制流。

### 三种返回结果

```javascript
TOUCH_RESULT = {
    PASS:      'pass',       // 不关我事，继续下一个中间件
    HANDLED:   'handled',    // 我处理了且消费了触点，管道停止
    INTERCEPT: 'intercept'   // 我处理了但触点可穿透，后续中间件也收到
}
```

### 管道三阶段

每个阶段有独立的中间件链：

```
handleTouchStart → [中间件链 A] → 停止或穿透
handleTouchMove  → [中间件链 B] → 停止或穿透
handleTouchEnd   → [中间件链 C] → 停止或穿透
```

每个中间件收到一个 `TouchContext` 对象，可以修改它，下个中间件看到的是修改后的上下文。

### TouchContext 设计

```javascript
{
    // 输入（由管道填充）
    x: 0, y: 0,                    // 触摸坐标
    touchId: null,                 // 触点标识
    timestamp: Date.now(),

    // 拦截上下文（由管道主循环管理，中间件不直接操作）
    phase: 'start',                // 'start' | 'move' | 'end'
    intercepted: false,            // 管道内部标记：上一中间件返回了 INTERCEPT

    // 只读数据（由管道注入，中间件不可修改）
    stars: [],             // 当前灵光数组
    playerEffects: {},     // 玩家效果状态（带 isStunned/... 方法）
    isGrounded: true       // 状态门：由 game.js 根据当前 state 决定

    // 管道本身
    stop: function() {},            // 立即停止管道
}
```

### 中间件注册（中间件链定义）

```javascript
// TouchStart 阶段中间件链
startChain = [
    groundGuard,                        // 兰姆达0：状态门（stunned/paused 等）
    rhythmSkillMiddleware,              // 兰姆达1：D4-节奏技（最高优先级）
    linkChainMiddleware,                // 兰姆达2：D4 联连触发灵光
    gestureMiddleware,                  // 兰姆达3：D2监控 / D3拖拽 / D4划链
    starClickMiddleware,                // 兰姆达4：D1 灵光点击（BattleEngine）
    poisonPuddleMiddleware              // 兰姆达5：毒液滩独立数组
];

// TouchMove 阶段中间件链
moveChain = [
    groundGuard,
    gestureMoveMiddleware,              // D2更新位移 / D3拖拽吸附 / D4划链追踪
];

// TouchEnd 阶段中间件链
// d1FallbackMiddleware 排在 gestureEndMiddleware 前面：monitoring 松手由 d1Fallback 处理并清除 _pendingFallbackStar；
// gestureEndMiddleware 只负责 charging/autoCast 场景下的残留清理（此时 d1Fallback 已返回 PASS）
endChain = [
    groundGuard,
    d1FallbackMiddleware,               // d1Fallback 兜底（监控期短触回退）
    gestureEndMiddleware,               // D2释放 / D3结算 / D4松手判定
];
```

### 兰姆达0：状态门（替换分散的 4 层打断检查 + 状态检查）

```javascript
function groundGuard(ctx) {
    var effects = ctx.playerEffects;

    // 统一打断检查 —— 只写一次
    if (effects.isStunned && effects.isStunned()) {
        ctx.stop();
        return TOUCH_RESULT.HANDLED;
    }

    // 统一闪避检查（如果将来需要阻止触摸）
    if (effects.isDodging && effects.isDodging()) {
        // 闪避中是否允许灵光点击，取决于设计
        // ctx.stop(); return TOUCH_RESULT.HANDLED;
    }

    // 非战斗状态全局阻断
    if (!ctx.isGrounded) {
        ctx.stop();
        return TOUCH_RESULT.HANDLED;
    }

    return TOUCH_RESULT.PASS;
}
```

所有"能点击吗？"的问题回答一次，放在管道的第一个中间件里。后续中间件不需要再检查打断、状态、暂停。`groundGuard` 同时注册在 start/move/end 三个链中——即使 TouchStart 时放行，后续 TouchMove/TouchEnd 阶段玩家状态也可能变化（移动过程中被 stunned），`groundGuard` 在每阶段都会重新检查。

### 兰姆达2：联连中间件

```javascript
function linkChainMiddleware(ctx) {
    // isReady(): 触发灵光可见，等待触摸激活
    if (linkChainSystem && linkChainSystem.isReady()) {
        if (linkChainSystem.handleTriggerTouch(ctx.x, ctx.y)) {
            // 触发成功 → beginLinkWindow 已设置 swipeActive=true
            // 继续让 gestureMiddleware 处理划链
            return TOUCH_RESULT.INTERCEPT;
        }
    }
    return TOUCH_RESULT.PASS;
}
```

### 兰姆达3：手势中间件（替换当前 TouchGestureSystem 的隐式状态机）

```javascript
function gestureMiddleware(ctx) {
    // 已有活动手势且是同一触点 → 幂等：更新位置，不重新分类
    if (activeGesture && activeGesture.touchId === ctx.touchId) {
        return TOUCH_RESULT.HANDLED;
    }

    // 清理上一个活动手势（多触点场景的安全网）
    if (activeGesture) {
        cancelActiveGesture();
    }

    // ── 手势分类 ──

    // D4 联连窗口激活 → 全屏划链
    if (linkChainSystem && linkChainSystem.isActive()) {
        beginSwipeTracking(ctx);
        return TOUCH_RESULT.INTERCEPT;
    }

    // 命中灵光
    var hitStar = hitTestStar(ctx.x, ctx.y, ctx.stars);
    if (hitStar) {
        if (chargeSystem && chargeSystem.isUnlocked()) {
            beginMonitoring(ctx, hitStar);
            // 注入到管道内部状态，供 TouchEnd 的 d1FallbackMiddleware 消费
            touchPipeline._pendingFallbackStar = hitStar;
            touchPipeline._pendingFallbackTouchId = ctx.touchId;
            touchPipeline._pendingFallbackOriginalTime = hitStar.disappearTime;
            return TOUCH_RESULT.HANDLED;
        }
        // D2 未解锁 → PASS，让 starClickMiddleware 处理
        return TOUCH_RESULT.PASS;
    }

    // 命中角色区域 → D3 拖拽
    if (dragSystem && dragSystem.isUnlocked() && dragSystem.isInCharacterArea(ctx.x, ctx.y)) {
        beginDrag(ctx);
        return TOUCH_RESULT.HANDLED;
    }

    return TOUCH_RESULT.PASS;
}
```

**`_pendingFallbackStar` 是跨生命周期桥接**：TouchStart 和 TouchEnd 是两次独立管道调用，各创建新的 `ctx`。监控期灵光引用必须存储在管道内部状态中，在 TouchEnd 时由 `d1FallbackMiddleware` 消费并清除。

**关键差异**：
- `INTERCEPT` 语义让 D4 联连和灵光点击共存
- 活动手势保护内置在中间件，不再依赖外部检查
- `ctx.stop()` 由状态门统一管理，手势中间件不关心打断
- `handleTriggerTouch` 和 `isActive` 划链追踪被分离到两个中间件（`linkChainMiddleware` 和 `gestureMiddleware`），职责清晰
- `cancelActiveGesture()` 定义：清理 `activeGesture` 状态（清除 d2TimerId、重置 type/touchId），**不调用** `chargeSystem.cancelCharge()`（ChargeSystem 的生命周期由 TouchEnd 的 `gestureEndMiddleware` 管理）。这意味着多触点场景下旧触点的手势被清理但监控状态保留——由各自触点的 TouchEnd 分别处理

### 兰姆达4：灵光点击中间件

```javascript
function starClickMiddleware(ctx) {
    // ctx.intercepted 由管道主循环在 INTERCEPT→HANDLED 后自动重置
    // 本中间件不关心是否被 intercept——总是委托给 NormalBattleAdapter
    return normalBattleAdapter.handleStarClick(ctx.x, ctx.y)
        ? TOUCH_RESULT.HANDLED
        : TOUCH_RESULT.PASS;
}
```

### 兰姆达：d1Fallback 中间件（TouchEnd 阶段）

```javascript
function d1FallbackMiddleware(ctx) {
    var star = touchPipeline._pendingFallbackStar;

    // 仅当 ChargeSystem 仍在 monitoring 阶段时才 d1Fallback
    // charging/autoCast 场景下：监控已转蓄力，由 releaseCharge 处理，不 d1Fallback
    if (star && touchPipeline._pendingFallbackTouchId === ctx.touchId
        && chargeSystem && chargeSystem.isMonitoring()) {

        // 首先取消 ChargeSystem 监控，清除状态避免泄漏（cancelCharge 内部已清除 _charging 标记）
        chargeSystem.cancelCharge();

        // 恢复灵光过期时间，使其可被正常命中
        star.disappearTime = touchPipeline._pendingFallbackOriginalTime || Date.now() + 5000;

        // 通过 NormalBattleAdapter 执行完整的状态同步 + 战斗逻辑
        // （SetTargetMonster / HP同步 / syncEngineStateBack 等）
        if (normalBattleAdapter) {
            normalBattleAdapter.handleStarClick(star.x, star.y);
        }

        touchPipeline._pendingFallbackStar = null;
        touchPipeline._pendingFallbackTouchId = null;
        touchPipeline._pendingFallbackOriginalTime = 0;
        return TOUCH_RESULT.HANDLED;
    }

    // charging/autoCast 场景：gestureEndMiddleware 会负责清理 _pendingFallbackStar
    return TOUCH_RESULT.PASS;
}
```

**关键设计**：
- 入口检查 `chargeSystem.isMonitoring()` 防止充电场景误触发
- 调用 `chargeSystem.cancelCharge()` 清除 ChargeSystem 内部状态（`state.monitoredStar` 等），防止状态泄漏
- 通过 `normalBattleAdapter.handleStarClick` 而非直接调 BattleEngine，保留完整的状态同步逻辑（SetTargetMonster、HP 同步、syncEngineStateBack）
- `_pendingFallbackStar` 存储在管道实例上，TouchStart 和 TouchEnd 是两次独立管道调用

### 兰姆达：手势结束中间件（TouchEnd 阶段）

```javascript
function gestureEndMiddleware(ctx) {
    // 委托 TouchGestureSystem 处理 D2释放/D3结算/D4松手判定
    if (touchGestureSystem) {
        touchGestureSystem.handleGestureEnd();
    }

    // 如果进入了蓄力（监控转蓄力），清理 _pendingFallbackStar——不会再 d1Fallback
    if (chargeSystem && (chargeSystem.isCharging() || chargeSystem.isAutoCast())) {
        touchPipeline._pendingFallbackStar = null;
        touchPipeline._pendingFallbackTouchId = null;
    }

    return TOUCH_RESULT.PASS;
}
```

### 管道主循环

```javascript
function runPipeline(chain, ctx) {
    for (var i = 0; i < chain.length; i++) {
        var result = chain[i](ctx);
        if (result === TOUCH_RESULT.HANDLED) {
            if (ctx.intercepted) {
                // INTERCEPT 后 HANDLED：ctx.intercepted 置 false，管道继续
                // 这允许 linkChainMiddleware(INTERCEPT) → gestureMiddleware(HANDLED) 后
                // starClickMiddleware 仍然执行（联连 + 灵光点击共存）
                ctx.intercepted = false;
                continue;
            }
            break;  // 正常 HANDLED：管道停止
        }
        if (result === TOUCH_RESULT.INTERCEPT) {
            ctx.intercepted = true;
            // 不设置 interceptedBy——ctx.intercepted 是一个布尔标记，不关心来源
            // 继续下一个中间件
        }
        // PASS：继续下一个
    }
}
```

**`ctx.intercepted` 语义**：是一个管道内的临时标记。当前中间件返回 `INTERCEPT` 时设置，后续中间件看到 `ctx.intercepted === true` 就知道前面有人"处理了但放行了"。如果后续中间件也在意这个信息（如联连触发后灵光点击仍需执行），不需要额外判断——管道自动让其继续。标记在一个 `HANDLED` 后被重置。退出管道后无意义。

## 四、问题修复映射

| 问题 | 如何在管道中消除 |
|------|-----------------|
| **问题1**：stunned 过期不自洽 | `groundGuard` 统一回答一次，调用 `effects.isStunned()` 方法。4 层分散过期 → 1 层统一过期。 |
| **问题2**：节奏阶段误吞 | `rhythmSkillMiddleware` 内部可返回 `PASS`（若未命中）让后续中间件处理。当前 `continue` 改为 `PASS`。 |
| **问题3**：`_charging` 标记泄露 | 独立修复：`cleanupExpiredStars` 中增加 `_charging` 超时保护（30 秒后强制清除）。管道不依赖 `_charging` 的清除时序。 |

| **问题5**：打断检查不一致 | `groundGuard` 统一一次。 |
| **问题6**：下落模式 y 限制 | 独立修复：`onBeforeStarClickHook` 放宽到 40%+设计坐标系。管道不涉及。 |
| **问题7**：活动手势冲突 | `gestureMiddleware` 顶部检查 `activeGesture.touchId`，已有活动手势直接 `HANDLED`（只更新不重新分类）。 |

    star._charging = false;
    star.disappearTime = Date.now() + 5000;  // 恢复为正常过期

`gestureMoveMiddleware` 是简单的委托：
```javascript
function gestureMoveMiddleware(ctx) {
    if (touchGestureSystem && ctx.x != null) {
        touchGestureSystem.handleGestureMove(ctx.x, ctx.y);
    }
    return TOUCH_RESULT.PASS;
}
```

**约束**：`handleGestureMove` 内部可能因手指大幅位移而取消 D2 监控（检测位移阈值后回调 `chargeSystem.cancelCharge` 或切换手势类型）。如果发生监控取消，管道上的 `_pendingFallbackStar`/`_pendingFallbackTouchId` 不会自动清除。实施时需确认：`handleGestureMove` 的位移取消路径是否通过 `activeGesture` 状态反映——管道可通过检查 `activeGesture.type !== 'monitoring'` 来知道监控已被取消，在 `d1FallbackMiddleware` 入口增加 `activeGesture.type === 'monitoring'` 保护即可，无需显式清除 `_pendingFallbackStar`。

### 管道内部状态

| 字段 | 类型 | 初始值 | 读写阶段 | 说明 |
|------|------|--------|---------|------|
| `_pendingFallbackStar` | `Star \| null` | `null` | TouchStart 写入，TouchEnd 消费清除 | 监控期灵光引用，桥接 TouchStart→TouchEnd |
| `_pendingFallbackTouchId` | `number \| null` | `null` | TouchStart 写入，TouchEnd 消费清除 | 对应触点标识，防止多触点串号 |
| `_pendingFallbackOriginalTime` | `number` | `0` | TouchStart 写入（`hitStar.disappearTime`） | d1Fallback 恢复 disappearTime 用 |
| `activeGesture` | `{ type, touchId } \| null` | `null` | gestureMiddleware 写入，cancelActiveGesture 清除 | 当前活动手势类型和触点 |
| `d2TimerId` | `number \| null` | `null` | beginMonitoring 设置，cancelActiveGesture 清除 | D2 150ms 监控 timer ID |

### 管道内部辅助函数

这些函数在 `TouchPipeline.js` 内部定义，挂载于管道实例：

- **`cancelActiveGesture()`**：清理 `activeGesture` 和 `d2TimerId`。不调用 `chargeSystem.cancelCharge()`——充电状态由各触点的 TouchEnd 分别管理。
- **`hitTestStar(x, y, stars)`**：遍历 `stars` 数组，从后往前做碰撞检测。命中半径规则同 5.3 节。返回命中的 star 对象或 null。**实现策略**：优先委托 `BattleEngine` 的碰撞检测方法（如果可静态调用），避免代码重复；作为降级方案在管道内部实现几何碰撞。注意：传给 BattleEngine 的 stars 数组应是管道注入的 `ctx.stars`，不依赖 `StarSystem.getStars()` 的全局状态。
- **`beginMonitoring(ctx, star)`**：委托 `chargeSystem.beginMonitoring(star)`，设置一个 150ms 的 `setTimeout` timer，存储在 `d2TimerId`。timer 回调逻辑：检查 `activeGesture` 是否仍为 `'monitoring'` 且 touchId 匹配（防止松手竞态），若是则调用 `chargeSystem.transitionToCharging()` 进入蓄力阶段。同时记录 `activeGesture = { type: 'monitoring', touchId: ctx.touchId }`。
- **`beginSwipeTracking(ctx)`**：委托 `touchGestureSystem` 进入 D4 划链追踪模式（调用划链专用的追踪初始化，非通用的 `handleGestureStart` 分类入口——管道已判定为 D4，不再重复分类）。记录 `activeGesture = { type: 'swipe', touchId: ctx.touchId }`。
- **`beginDrag(ctx)`**：委托 `dragSystem.beginDrag(ctx.x, ctx.y)`，记录 `activeGesture = { type: 'drag', touchId: ctx.touchId }`。

## 九、四维度自证

### 管理性

- 中间件链是一个数组定义，一看就知道触摸优先级顺序是什么
- 管道入口在 `game.js` 中只有 3 行（`createContext` + `runXxx`），而不是 80 行的 if-else 树
- "谁在处理触摸" 的问题通过读中间件链数组即可回答，不需要在 4 个文件中跳转
- 调试：在管道主循环中加一行 `_log` 就能看到每个触点经过了哪些中间件

### 维护性

- 每个中间件的核心逻辑接受 `ctx` 返回 `TOUCH_RESULT`，与其他中间件解耦
- `chargeSystem` 不需要被注入到 `TouchGestureSystem`、`NormalBattleAdapter`、`BattleEngine` 三层 —— 只有 `gestureMiddleware` 和 `d1FallbackMiddleware` 需要引用它
- 修改一个中间件的逻辑不会破坏另一个中间件
- 状态门（打断/闪避/暂停）只写一次，修改一次生效全管道

### 扩展性

- 新增消费者 = 写一个中间件函数 + 在数组中加一行
- 调整优先级 = 在数组中移动位置
- 新增管道阶段（如 `TouchCancel`）= 加一个链数组，已有的中间件可以复用
- 中间件可以返回 `INTERCEPT` 实现"消费但穿透"的语义，不需要 hack（当前的 `continue` 之后还要手动调用下一个系统）

### 统一性

- 所有"触摸前检查"收敛到 `groundGuard` 一个位置
- 所有"我是谁、我是否要消费这个触点"的回答收敛到 `TOUCH_RESULT` 三种语义
- 所有"跨生命周期状态传递"收敛到管道实例的显式字段（`_pendingFallbackStar` 等），不再依赖 `star._charging` 的时序
- 管道是纯数据流驱动：`ctx` 进 → 中间件链 → `ctx` 出。没有隐式的全局状态依赖

## 十、不改动的说明

以下逻辑经分析属于设计意图，管道的引入不改变它们的语义：

- **D2 150ms 监控延迟**：蓄力/点击二义性的正确解法，在 `gestureMiddleware` 中保持不变
- **BattleEngine 碰撞检测从后往前遍历**：保证最上层的灵光优先命中，和管道无关
- **联连触发灵光 40px 命中半径**：精确操作设计，和管道无关

## 十一、审计说明

### 第三轮审计（管道方案完整性审计）

1. **`handleStarClickAtStar` 方法不存在**：`NormalBattleAdapter` 只有 `handleStarClick(touchX, touchY)` 签名。改为利用 `BattleEngine.handleStarClick` 已有的 `externalStars` 参数：传入 `handleStarClick(star.x, star.y, [star])` 构造单灵光数组。（**已在第五轮#18中修正**：回退为通过 `normalBattleAdapter.handleStarClick(star.x, star.y)` 执行 d1Fallback，保留 Adapter 的状态同步逻辑。）

2. **`d1FallbackTarget` 跨生命周期传递缺失**：TouchStart 和 TouchEnd 是两次独立管道调用，各创建新的 `ctx`。`d1FallbackTarget` 不能放在 `ctx` 上。改为管道实例上的内部状态 `touchPipeline._pendingFallbackStar` + `touchPipeline._pendingFallbackTouchId`，由 `gestureMiddleware` 在 TouchStart 时写入，`d1FallbackMiddleware` 在 TouchEnd 时消费并清除。

3. **`starClickMiddleware.interceptedBy` 条件写错**：`gestureMiddleware` 在 D2 监控时返回 `HANDLED`（非 `INTERCEPT`），`ctx.interceptedBy` 不会设为 `'gestureMiddleware'`。改为移除无效条件，`starClickMiddleware` 简化为直接委托。

4. **`linkChainMiddleware` 缺失具体实现**：原文档只给了注册位置但没有中间件逻辑。补充完整：`isReady()` 阶段调用 `handleTriggerTouch`，命中后返回 `INTERCEPT`。

5. **`gestureMiddleware` 的 D4 联连判定**：`isActive()`（划链活跃中）和 `isReady()`（触发灵光等待）是两个阶段。`linkChainMiddleware` 处理 `isReady()`（触发灵光命中），`gestureMiddleware` 处理 `isActive()`（全屏划链追踪）。

6. **迁移阶段3删除 BattleEngine 的 stunned 检查有风险**：BattleEngine 可能有非触摸入口（脚本直接调用 `handleStarClick`）。改为保留 BattleEngine 的独立检查作为防御层，仅删除 TouchGestureSystem 和 NormalBattleAdapter 中的重复检查。

### 第四轮审计（实施可行性审计）

7. **`d1FallbackMiddleware` 调用路径不畅通**：`NormalBattleAdapter.handleStarClick` 只有 `(touchX, touchY)` 签名，内部固定传 `getStars()`。传入 `[star]` 第三参数无效。改为绕过 Adapter 直接调 `BattleEngine.handleStarClick(star.x, star.y, [star])`。管道需要注入 `BattleEngine` 引用（`touchPipeline._battleEngine`）。（**已在第五轮#18中修正**：回退为通过 `normalBattleAdapter.handleStarClick(star.x, star.y)` 执行 d1Fallback，管道不再需要注入 `BattleEngine` 引用。）

8. **`_originalDisappearTime` 字段不存在**：`ChargeSystem.beginMonitoring` 只把原始时间存在 `state.originalDisappearTime`（内部状态），不存到 `star` 上。改为在 `gestureMiddleware` 的 `beginMonitoring` 调用前显式复制：`touchPipeline._pendingFallbackOriginalTime = hitStar.disappearTime`。

9. **`_pendingFallbackStar` 泄漏路径**：用户按住超过 150ms 进入蓄力后松手，不会再走 d1Fallback。但 `_pendingFallbackStar` 仍持有灵光引用。新增 `gestureEndMiddleware`——在 TouchEnd 时检查蓄力/施法状态，清除挂起的 fallback。

32. **`hitTestStar` 碰撞检测与 BattleEngine/TouchGestureSystem 的检测逻辑重复**：管道内部的 `hitTestStar` 需要再实现一份命中半径逻辑（同 5.3 节），不能直接复用现有系统的碰撞检测——因为现有系统的检测方法和灵光状态（`_charging` 等）耦合。修正：在辅助函数 `hitTestStar` 说明中追加实现策略——优先委托 BattleEngine 的碰撞检测静态方法，降级方案在管道内实现纯几何碰撞，使用管道注入的 `ctx.stars`。

33. **D2 监控期中 TouchMove 大幅位移导致 `_pendingFallbackStar` 泄漏**：`gestureMoveMiddleware` 委托 `touchGestureSystem.handleGestureMove`，但 `handleGestureMove` 内部可能因位移阈值触发 `cancelCharge` 或切换手势类型。修正：在 `gestureMoveMiddleware` 后追加约束说明——管道可通过检查 `activeGesture.type !== 'monitoring'` 在 `d1FallbackMiddleware` 入口保护，避免依赖显式清除。
