# 护盾灵光点击后护盾条不显示 — 问题分析与解决方案

## 一、问题现象

战斗中点击护盾类灵光（如"守灵光" `skill_shield`）后，玩家血条上方预期的冰蓝色护盾条未出现。

---

## 三、根因分析

### 根因 A（最可能）：渲染器与 game.js 双重 update() 的覆盖时序不稳定

**现象**：`GameBattleRenderer.renderGame()` 和 `game.js` 渲染主循环各调用一次 `normalBattleAdapter.update()`，其中 `update()` 内部执行 `engine.setPlayerState(hp, shield)` 将 `pd.playerShield` 覆盖到 `S.playerShield`。

```211:213:e:\AIGame\V1\src\renderers\GameBattleRenderer.js
        var normalBattleAdapter = getNormalBattleAdapter();
        if ((state === GAME_STATE.PLAYING || state === GAME_STATE.SEASON_PLAYING || state === GAME_STATE.STAGE_PLAYING) && normalBattleAdapter) {
            normalBattleAdapter.update();
        }
```

```5977:5979:e:\AIGame\V1\game.js
        if (isCombat) {
            // BattleEngine 每帧 tick（处理 pendingDeaths、攻击者、时间倒计时等）
            if (normalBattleAdapter) normalBattleAdapter.update();
        }
```

**影响**：每帧调用两次 `setPlayerState` 不会丢数据（因为 `pd` 在第一帧同步后就是正确值），但如果在某些帧之间、某个异步流程中 `pd.playerShield` 被暂时修改为旧值或不正确值，这个双重覆盖会放大问题。

### 根因 B：GameLifecycleSystem.startGame() 强制清零的时机

```244:244:e:\AIGame\V1\src\systems\GameLifecycleSystem.js
        pd.playerShield = 0;
```

`pd.playerShield = 0` 之后约 70 行代码，才调用 `normalBattleAdapter.init()`。而 `init()` 中传入 `playerShield: pd.playerShield || 0`，此时当然是 0，这是正常的。

但如果 `startGame()` 在战斗中因某种原因被重新调用（如场景切换、异常恢复），护盾会丢失。这不是预期流程，但需要排查是否存在此类意外调用。

### 根因 C：塔模式的 `|| 0` 防护写法隐含风险

```296:296:e:\AIGame\V1\src\renderers\GameBattleRenderer.js
                pd.playerShield = towerSystem.playerShield || 0;
```

`towerSystem.playerShield` 被声明为 `var playerShield = 0`（TowerSystem.js 第228行），数值正常。但 `|| 0` 写法会把所有 falsy 值转为 0。如果该变量在某些边界条件下变成 `undefined`（比如战斗结束被清理但引用未更新），会导致护盾被清零。

### 根因 D（最可疑）：特定历史版本的 `setPlayerState` 签名变更带来的副作用

在提交 `16587bb`（BattleEngine状态解耦）中，`setPlayerState` 从 6 参数改为 2 参数：

```
- function setPlayerState(hp, shield, dodging, dodgeEndTime, stunned, stunEndTime) {
+ function setPlayerState(hp, shield) {
```

如果存在其他调用方仍传入了额外的位置参数——虽然 JS 的 `arguments` 不会因此报错，但如果某些调用方依赖了旧的参数映射逻辑，可能导致行为异常。

经排查，现有代码中所有调用方（`NormalBattleAdapter.update()`、`TowerSystem` 同步等）都只传 `(hp, shield)`，不受影响。但遗留的旧代码引用仍是一个潜在风险。

### 根因 E：技能系统路径 vs 灵光星点击路径的偏差

两条路径对 `playerShield` 的加持有根本性差异：

| 路径 | 操作目标 | 同步方式 |
|------|----------|----------|
| 技能"守灵光"（SkillSystem） | 直接 `pd.playerShield += shieldAmount` | 不经过 BattleEngine，通过 `update()` 的 setPlayerState 单向同步 |
| 灵光星点击（BattleEngine） | `S.playerShield += shieldAmt` | 通过 `syncEngineStateBack()` 回写 pd |

技能路径直接修改 `pd.playerShield`，而灵光星点击路径需要 `syncEngineStateBack` 回写。如果 `syncEngineStateBack` 被跳过（例如 `handleStarClick` 返回 false），灵光星点击后的护盾值不会持久化。

**验证方法**：在 `syncEngineStateBack` 入口添加日志，查看护盾灵光被点击后是否确实调用了回写。

## 四、方案：统一真相源为 pd，消除双向同步

### 4.1 核心思路

`playerHp` 已经是 `pd` 为唯一真相源、BattleEngine 只读取的成功范式。`playerShield` 当前的问题恰恰在于没有遵循这个模式——它有三个并行的归属（`pd.playerShield`、`S.playerShield`、`TowerSystem.playerShield`），通过双向同步互相覆盖。

统一后只有一个真相源 `pd.playerShield`：
- **写入**：所有代码直接改 `pd.playerShield`（BattleEngine 通过 getter/setter 回调操作）
- **读取**：渲染器、BattleEngine、TowerSystem 都只读 `pd.playerShield`
- **消除**：`syncEngineStateBack` 中关于 shield 的回写、`setPlayerState` 中 shield 的覆盖、TowerSystem 的局部 `playerShield` 变量

### 4.2 BattleEngine 改动

**A. 新增 shield getter/setter 注入点**

在 `BattleEngine` 顶部 deps 区域新增两个依赖：

```javascript
var getPlayerShield = deps.getPlayerShield;  // () → number
var setPlayerShield = deps.setPlayerShield;  // (number) → void
```

**B. init() 中不再从 config 初始化 S.playerShield**

删除 `S.playerShield = config.playerShield;`（第 706 行）。改为：

```javascript
if (config.playerShield !== undefined) setPlayerShield(config.playerShield);
```

**C. handleSpecialStar('shield') 改为直接操作 pd**

当前代码（第 570-577 行）：

```javascript
case 'shield':
    var shieldAmt = Math.floor(maxHp * shieldPct);
    S.playerShield = (S.playerShield || 0) + shieldAmt;
```

改为：

```javascript
case 'shield':
    var shieldAmt = Math.floor(maxHp * shieldPct);
    setPlayerShield(getPlayerShield() + shieldAmt);
```

**D. 所有 S.playerShield 读/减操作改为通过 getter/setter**

| 当前代码 | 改为 |
|----------|------|
| `if (S.playerShield > 0)` → 伤害吸收 | `var sh = getPlayerShield(); if (sh > 0)` |
| `S.playerShield -= absorb` | `setPlayerShield(sh - absorb)` |
| `S.playerShield = (S.playerShield \|\| 0) + skill.shield`（技能 useSkill） | `setPlayerShield(getPlayerShield() + skill.shield)` |

涉及位置：第 256、278-280、469-471、575、590-592、1095 行。

**E. setPlayerState 移除 shield 参数**

`setPlayerState(hp, shield)` 改为 `setPlayerState(hp)`。删除第 1224 行 `if (shield !== undefined) S.playerShield = shield;`。

**F. getState() 无需改动**

`getState()` 当前为 `return S`，不需要修改。统一后 `S` 不再持有 `playerShield`，外部通过 `es.playerShield` 读取会得到 `undefined`——但所有外部对 `es.playerShield` 的读取已在 4.3D（NormalBattleAdapter）和 4.4（TowerSystem 第 1330 行）中删除，不会产生错误。

**G. createDefaultState() 移除 playerShield 字段**

第 117 行 `playerShield: 0` 删除——`S` 对象不再持有 shield。

### 4.3 NormalBattleAdapter 改动

**A. buildEngineDeps() 新增 shield getter/setter**

在第 256 行（setPlayerPoisonTickTime 之后）追加：

```javascript
getPlayerShield: function() { return getSaveData().playerShield || 0; },
setPlayerShield: function(v) { getSaveData().playerShield = v; },
```

**B. init() 调整**

`playerShield: pd.playerShield || 0` 保持不变——init 传 config 是为了触发 BattleEngine.init 中的 `setPlayerShield(config.playerShield)` 清零初始化。

**C. update() 删除 shield 同步**

`battleEngine.setPlayerState(hp, shield)` 改为 `battleEngine.setPlayerState(hp)`。

第 926-933 行中 shield 的局部变量计算可以删除。

**D. syncEngineStateBack() 删除 shield 回写**

删除 `pd.playerShield = es.playerShield;`（第 1064 行）和 `ts.playerShield = es.playerShield;`（第 1059 行）。shield 不再需要从引擎回写——真相源是 pd，引擎的任何修改已经通过 setter 直接写入了 pd。

**E. handleStarClick() 删除 shieldToSync 计算**

第 984-993 行的 `shieldToSync` 变量不再需要（setPlayerState 不再接受 shield 参数）。

### 4.4 TowerSystem 改动

**删除局部变量 `var playerShield = 0;`**（第 228 行），所有 14 处对局部变量 `playerShield` 的引用改为直接操作 `getSaveData().playerShield`：

| 行号 | 当前代码 | 改为 |
|------|----------|------|
| 980 | `playerShield: 0`（init config） | `playerShield: getSaveData().playerShield \|\| 0` |
| 1102 | `var currentShield = playerShield` | `var currentShield = getSaveData().playerShield \|\| 0` |
| 1113 | `battleEngine.setPlayerState(currentHp, currentShield)` | `battleEngine.setPlayerState(currentHp)` |
| 1116 | `playerShield = currentShield` | `getSaveData().playerShield = currentShield` |
| 1153 | `var poisonLabel = playerShield > 0 ? ...` | `var poisonLabel = getSaveData().playerShield > 0 ? ...` |
| 1181 | `battleEngine.setPlayerState(playerHp, playerShield)`（战斗 tick 同步） | 删除此行（不再需要） |
| 1272 | `playerShield = (playerShield \|\| 0) + shieldAmt` | `getSaveData().playerShield = (getSaveData().playerShield \|\| 0) + shieldAmt` |
| 1330 | `playerShield = st.playerShield`（从 engine getState 回读） | 删除此行（真相源已是 pd，无需同步） |

**注意**：第 1181 行和 1330 行是 **直接删除**，不是替换。这两行是旧的双向同步残留——统一后引擎不再持有 shield，不需要也不应该从引擎同步。

### 4.5 BossBattleAdapter 改动

BossBattleAdapter 大部分 shield 操作已经直接读写 `pd.playerShield`，无需改动。需要改的只有两处：

| 行号 | 当前代码 | 改为 |
|------|----------|------|
| 636 | `playerShield: 0`（init config） | `playerShield: getSaveData().playerShield \|\| 0` |
| 830 | `pd.playerShield = S.playerShield;`（从引擎回写） | 删除此行（真相源已是 pd） |

### 4.6 GameBattleRenderer 改动

**渲染无需改动**——它本来就只读 `pd.playerShield`（第 838 行）。

**删除塔模式中对 pd.playerShield 的额外覆盖**（第 290、296 行）：这些行是从 engine/tower 回写 shield 到 pd。统一后不再需要——塔模式修改 shield 会直接写 pd。

### 4.7 其他文件的战损吸收逻辑

`StarThiefSystem.js`、`BossStarSystem.js`、`game.js` 中毒星处理——这些文件已经在直接操作 `pd.playerShield`（消耗护盾），无需改动。
