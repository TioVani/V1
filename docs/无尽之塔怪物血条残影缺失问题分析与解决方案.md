# 无尽之塔怪物血条半透明残影缺失问题分析与解决方案

## 问题现象

普通模式、Boss 模式、赛季模式、闯关模式下，怪物掉血时血条会有白色半透明"残影血条"缓慢衰减的效果。而无尽之塔模式下，怪物血条掉血后直接缩短，没有白色残影效果。

## 根因分析

问题有三层原因，层层叠加导致残影效果完全失效。

### 第一层：renderBattle 函数从未被调用

`TowerRenderer.js` 中的 `renderBattle()` 函数内部已经正确实现了血条残影逻辑（第 448-458 行，使用 `_towerHpTracker.get(monster, ...)` 跟踪怪物 HP 并绘制白色残影血条）。但由于渲染调度方式的问题，这个函数**从未在渲染循环中被调用**。

在 `game.js:5704`：

```javascript
render._dispatch[GAME_STATE.TOWER_COMBAT] = renderGame;
```

TOWER_COMBAT 状态走的是 `renderGame`（即 `GameBattleRenderer.renderGame()`），而不是 `TowerRenderer.renderBattle()`。而 `renderBattle` 的包装函数（`game.js:2497`）虽然被定义，但从未被注册进渲染分发器。这层本身不是直接原因，但说明了为什么 TowerRenderer 中已实现的残影逻辑没有生效。

### 第二层（根本原因）：renderGame 中怪物对象每帧被复制为全新对象

`GameBattleRenderer.renderGame()` 在 TOWER_COMBAT 分支中（`GameBattleRenderer.js:270-274`）：

```javascript
var tMonCopy = Object.assign({}, tMon);
tMonCopy._isCopy = true;
// ...
setMonsters([tMonCopy]);
```

每帧都通过 `Object.assign` 创建一个**全新对象**放入 `monsters` 全局数组。而怪物血条残影的绘制经由以下链路：

1. `GameBattleRenderer.renderGame()` → `drawMonster()`（game.js:982）
2. `drawMonster()` → `monsterDrawRenderer.drawMonster()`（game.js:1900）
3. `MonsterDrawRenderer.drawMonster()` → `getActiveMonsters()` → `monsterSpawnSystem.getActiveMonsters()` → 返回 `monsters` 全局数组中 active 的元素
4. `MonsterDrawRenderer.drawSingleMonster(m, ...)` → `_monsterHpTracker.get(m, m.hp, m.maxHp)`（MonsterDrawRenderer.js:174）

其中 `_monsterHpTracker` 是基于 `WeakMap` 以**对象引用**为 key 的（`DelayedHpTracker.js`）。每帧都是新对象 → `WeakMap` 中每次都是新 key → `delayedHp` 每次都初始化为 `currentHp` → 白色残影血条永远不会绘制。

### 第三层（不是问题）：BattleEngine 不替换 monster 引用

`TowerSystem.updateCombatTick()` 中 `combatMonster = st.monster`（TowerSystem.js:1326）每帧从 BattleEngine 同步 monster 状态。BattleEngine 中 `S.monster` 只在 `init`（传入 `config.monster` 直接引用）、`replaceMonster` 和 `setTargetMonster` 时赋值。经核查，TowerSystem 从未调用这些替换方法，所以每帧同步回来的 `st.monster` 始终是同一个对象——即 `encounterMonster` 中创建的 `combatMonster`。

这意味着 `combatMonster` 的引用在整场战斗中保持不变。如果渲染直接使用 `combatMonster` 原引用（而非 `Object.assign` 副本），`DelayedHpTracker` 可以正确跟踪。

### 完整因果链总结

```
TOWER_COMBAT 渲染循环
    → renderGame (GameBattleRenderer)
        → 每帧 Object.assign 复制 combatMonster → setMonsters([副本])
            → MonsterDrawRenderer.drawSingleMonster()
                → _monsterHpTracker.get(副本, hp, maxHp)
                    → WeakMap 中 key 是每帧的新对象 → delayedHp 永远 == currentHp
                        → 白色残影血条永远不会绘制
```

## 解决方案

### 方案评估

之前的方案（直接使用 `combatMonster` 原引用、去掉 `Object.assign`）虽然能解决问题，但存在架构隐患：

- `monsters` 全局数组由 `MonsterSpawnSystem` 管理，在 TOWER_COMBAT 下被 `renderGame` 每帧覆盖注入外部对象，同一变量承载两种语义，耦合隐蔽。
- 往 TowerSystem 内部对象上写渲染属性（`x`、`y`、`size`），混淆数据层和渲染层边界。
- 将来任何新的战斗模式借道 `renderGame` + `setMonsters` 都会遇到同类对象引用问题，无法复用到其他模式。

### 推荐方案：让 DelayedHpTracker 支持按稳定 ID 跟踪

核心思路：**不改变现有的对象复制行为，而是让跟踪器不依赖对象引用稳定性。**

#### 1. 修改 `DelayedHpTracker` — 增加 `getById` 方法

```javascript
// V1/src/utils/DelayedHpTracker.js

function createDelayedHpTracker() {
    var weakCache = new WeakMap();       // 原 get() 使用的对象引用缓存
    var idCache = new Map();             // 新增：字符串 ID → { delayedHp, maxHp }

    function get(entity, currentHp, maxHp) {
        // 现有逻辑不变，使用 weakCache
        // ...
    }

    function getById(id, currentHp, maxHp) {
        currentHp = Math.max(0, currentHp);
        var entry = idCache.get(id);

        if (!entry || entry.maxHp !== maxHp) {
            entry = { delayedHp: currentHp, maxHp: maxHp };
            idCache.set(id, entry);
        }

        if (currentHp > entry.delayedHp) {
            entry.delayedHp = currentHp;
        }

        if (entry.delayedHp > currentHp) {
            entry.delayedHp -= (entry.delayedHp - currentHp) * 0.06;
            if (entry.delayedHp - currentHp < 0.5) {
                entry.delayedHp = currentHp;
            }
        }

        return {
            delayedHp: entry.delayedHp,
            ratio: maxHp > 0 ? entry.delayedHp / maxHp : 0
        };
    }

    function reset(entity) {
        if (entity) weakCache.delete(entity);
    }

    function resetById(id) {
        idCache.delete(id);
    }

    function resetAll() {
        weakCache = new WeakMap();
        idCache = new Map();
    }

    return {
        get: get,
        getById: getById,
        reset: reset,
        resetById: resetById,
        resetAll: resetAll
    };
}
```

#### 2. 修改 `TowerSystem` — 进入战斗时分配稳定 ID

在 `encounterMonster`（约第 927 行）中，`combatMonster` 创建后立即分配一个战斗实例 ID：

```javascript
// TowerSystem.js — encounterMonster 函数内
combatMonster = {};
for (let key in cell.monster) {
    combatMonster[key] = cell.monster[key];
}
// 新增：分配战斗实例 ID（用于 DelayedHpTracker 按 ID 跟踪）
combatMonster._combatInstanceId = 'tower_' + currentFloor + '_' + cell.x + '_' + cell.y + '_' + Date.now();
```

隐藏之路 Boss 同样需要（约第 1801 行）：

```javascript
combatMonster = {};
for (let key in cell.guardian) {
    combatMonster[key] = cell.guardian[key];
}
combatMonster._combatInstanceId = 'tower_hidden_' + currentFloor + '_' + Date.now();
```

#### 3. 修改 `MonsterDrawRenderer` — HP 跟踪时优先使用 ID

在 `drawSingleMonster` 中（约第 174 行），白色残影血条部分：

```javascript
// 当前代码
var _mDelay = _monsterHpTracker.get(m, m.hp, m.maxHp);

// 改为
var _mDelay;
if (m._combatInstanceId) {
    _mDelay = _monsterHpTracker.getById(m._combatInstanceId, m.hp, m.maxHp);
} else {
    _mDelay = _monsterHpTracker.get(m, m.hp, m.maxHp);
}
```

### 方案优势

| 维度 | 之前方案（去 Object.assign） | 推荐方案（ID 跟踪） |
|---|---|---|
| **统一性** | 塔模式特例——全局数组语义分裂 | 所有模式走同一路径，`Object.assign` 副本行为不变 |
| **扩展性** | 新战斗模式需要审查对象引用稳定性 | 新模式只需分配一个 `_combatInstanceId` 即可获得残影 |
| **维护性** | 依赖"对象引用不变"的隐含约定，无文档无报错 | ID 是显式契约，丢失 ID 时有回退路径（`get` 作为 fallback） |
| **数据隔离** | 直接污染 TowerSystem 内部对象属性 | TowerSystem 只写一个它拥有的字段（`_combatInstanceId`） |
| **改动面** | 1 个文件，10 行 | 3 个文件，总约 40 行 |

### 为什么不直接用 TowerRenderer.renderBattle()

`TowerRenderer.renderBattle()` 内部也正确实现了血条残影（使用独立的 `_towerHpTracker` 实例），但它的渲染逻辑（怪物绘制、星星渲染、动画系统等）与 `GameBattleRenderer.renderGame()` 不完全一致，直接切换到它可能导致其他渲染效果缺失。

### 为什么不在 GameBattleRenderer 中直接调用 TowerRenderer.renderBattle 的怪物绘制部分

这需要拆出 `TowerRenderer` 的怪物绘制为一个独立模块，改动面大，且不利于统一其他战斗模式的渲染行为。

### 修改影响范围

| 文件 | 改动 |
|---|---|
| `V1/src/utils/DelayedHpTracker.js` | 新增 `getById`/`resetById`，Map 从 WeakMap 改为支持字符串 key（保留原有 WeakMap 兼容） |
| `V1/src/systems/TowerSystem.js` | `encounterMonster` 和隐藏之路入口各加 1 行 ID 赋值 |
| `V1/src/renderers/MonsterDrawRenderer.js` | 1 处条件判断：有 `_combatInstanceId` 用 `getById`，否则用 `get` |
| `V1/src/renderers/GameBattleRenderer.js` | **不需要修改**，现有 `Object.assign` 行为保持不变 |

- 不影响玩家血条残影效果（玩家血条使用 `_battleHpTracker`，不需要 ID）
- 不影响普通模式怪物血条残影（普通怪物对象引用稳定，走 `get` 回退路径，行为不变）

> **内存说明**：`getById` 使用 `Map` 以字符串为 key，战斗结束后旧条目不会自动回收。但每个条目仅存储 `{ delayedHp, maxHp }`（约 32 字节），单次游玩最多产生几十条，内存影响可忽略。如需更严格的生命周期管理，可在 `MonsterDrawRenderer.drawMonster()` 中比对当前活怪物和已缓存 ID，清理不再活跃的条目。
