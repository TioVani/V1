# 击杀回血机制方案

## 概述

每击败一个怪物，回复玩家最大生命值的 2%。

## 架构选型

### 方案：独立 Plugin 模块 + 单行接入

参照 `StarThiefSystem` 的接入方式——在 `NormalBattleAdapter.handleMonsterDeath()` 的结算末尾，调用一行 hook 即可。不侵入怪物死亡结算的主流程。

### 模块结构

```
src/systems/
  VictoryHealPlugin.js          ← 新增：击杀回血插件（配置 + 逻辑）
  NormalBattleAdapter.js        ← 修改：加 1 行 hook 调用 + deps 声明
```

### 数据流

```
怪物死亡 → NormalBattleAdapter.handleMonsterDeath()
  → (所有现有结算：分数/金币/掉落/任务...)
  → VictoryHealPlugin.onKill(playerData, monsterType, extra)
    - extra 包含：addMessage / battleEngine / getCharacterFullStats
    → 读配置：healPercent（默认 0.02）
    → 取最大血量：getCharacterFullStats(charId).hp
    → 计算回复量：Math.max(Math.floor(maxHp * healPercent), MIN_HEAL)
    → playerData.playerHp = Math.min(currentHp + healAmount, maxHp)
    → battleEngine.setPlayerState(newHp)     ← 必须：防止下帧 syncEngineStateBack 覆盖
    → addMessage("+XX 灵能", '#00ff88')
```

### 为什么必须同步引擎

`NormalBattleAdapter.handleStarClick()` 每次执行时从 `pd.playerHp` 读值推入引擎，`syncEngineStateBack()` 又会用引擎值覆盖 `pd.playerHp`。如果只写 `playerData.playerHp` 不写 `battleEngine.setPlayerState()`，下一次星星点击会把回血吞掉。参照已有的窃灵冠回血模式（`NormalBattleAdapter.js` 第 1473-1474 行）。

## 配置项

所有可调参数集中在 `VictoryHealPlugin.js` 顶部常量区：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `HEAL_PERCENT` | `0.02` | 每次击杀回复最大血量比例 |
| `MIN_HEAL` | `1` | 单次最低回复量（防低级角色回复为 0） |
| `ENABLED` | `true` | 总开关，设为 `false` 即禁用整个机制 |
| `SHOW_MESSAGE` | `true` | 是否显示飘字提示 |

## 接入点（需同时覆盖两处）

### 接入点 A：常规/赛季模式（主路径）

在 `NormalBattleAdapter.js` 的 `handleMonsterDeath()` 中，第 1312 行 `updateTaskProgress('kill_monsters', 1)` 之后、`savePlayerDataFn()` 之前插入：

```
victoryHealPlugin.onKill(playerData, monsterType, extra);
```

### 接入点 B：分裂 Boss 最后一只小怪（独立分支）

`handleMonsterDeath()` 的第 1198-1211 行，分裂 Boss 的剩余小怪走独立分支（检测 `isSplitFromBoss`），不走主路径。当最后一只分裂小怪被击杀时（`hasMoreSplit` 为 false，进入 `addMessage('所有分裂小怪已击败!')` 分支），此处也需要插入回血调用。

该分支在第 1207 行已有 `updateTaskProgress('kill_monsters', 1)`，在其后同样插入：

```
victoryHealPlugin.onKill(playerData, monsterType, extra);
```

### 不需要接入的点

- **分裂母体提前 return**（第 1160 行）：分裂时母体未真正死亡，不回血——设计正确。
- **教学战斗**（第 1093 行 `return`）：教学战跳过——设计正确。

### 暂不接入、预留位置的模式

**Stage 模式**（第 1249 行 `return`）：第一阶段 `GAME_STATE.STAGE_PLAYING` 检测到后在第 1246 行调用 `stageSys.onMonsterDefeated(m)` 并立即 return，跳过了主路径（接入点 A 不会触发）。后续如需在 Stage 模式启用回血，在 `stageSys.onMonsterDefeated(m)` 之前插入：

```
victoryHealPlugin.onKill(playerData, monsterType, extra);
```

## 插件 API 设计

```js
// VictoryHealPlugin.js — 工厂函数
export function createVictoryHealPlugin(deps) { ... }

// deps 内容（由 game.js 注入，转传给 adapter，再转传给 onKill）
deps: {
    addMessage: function,
    getBattleEngine: function,  // 返回 battleEngine 实例或 null
    getCharacterFullStats: function
}

// onKill 签名
function onKill(playerData, monsterType, opts) {
    // opts: { addMessage, battleEngine, getCharacterFullStats }
    if (!ENABLED) return;
    var stats = opts.getCharacterFullStats(playerData.currentCharacterId);
    var maxHp = stats ? stats.hp : 100;
    var healAmount = Math.max(Math.floor(maxHp * HEAL_PERCENT), MIN_HEAL);
    playerData.playerHp = Math.min(playerData.playerHp + healAmount, maxHp);
    if (opts.battleEngine) opts.battleEngine.setPlayerState(playerData.playerHp);
    if (SHOW_MESSAGE) opts.addMessage('+' + healAmount + ' 灵能', '#00ff88');
}
```

## 调用链总览

```
game.js
  → createVictoryHealPlugin({ addMessage, getBattleEngine, getCharacterFullStats })
  → 产出 victoryHealPlugin 实例
  → 传入 createNormalBattleAdapter(deps) 的 deps 中
  → adapter 内部在 handleMonsterDeath() 末尾调用 victoryHealPlugin.onKill()
```

## 飘字表现

回复时显示绿色飘字：`+XX 灵能`，使用已有 `addMessage` 接口。

## 与现有系统的关系

- **FaithSystem.healOnKill**：已配置数据（每杀回复 5 点）但未接入结算流程。本方案实现后，FaithSystem 的 `healOnKill` 可直接在 `onKill` 中作为加成系数。
- **窃灵冠（thief_crown）**：已有的暴击回血（固定 5 点），与本方案的百分比回血独立叠加、互不冲突。
